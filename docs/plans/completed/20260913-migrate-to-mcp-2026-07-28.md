# Migrate to MCP `2026-07-28`

## Overview

Migrate the stdio MCP server from the `2025-11-25` protocol target to the stateless MCP `2026-07-28` protocol revision using the official Go SDK. Modern requests will use `server/discover` and per-request protocol/client metadata without an initialization handshake, while `2025-11-25` clients retain tested legacy negotiation. The existing tool catalog and domain behavior remain unchanged except that `stratz_server_info` will report both the preferred protocol version and the complete advertised version set.

## Repository Context

- `go.mod` and `go.sum` — currently pin `github.com/modelcontextprotocol/go-sdk` v1.6.1; v1.7.0 is the first stable release with full MCP `2026-07-28` support and legacy fallback.
- `docs/tool-contracts.json` — canonical protocol target and `stratz_server_info` output schema; generated contract files must not be edited directly.
- `internal/contractgen/generator.go` — validates the exact protocol and contract versions and emits protocol constants, Go types, fixtures, manifests, and reference documentation.
- `internal/mcp/server.go` — constructs the static SDK server and serves stdio; the SDK automatically implements `server/discover`, validates per-request metadata, and emits response metadata.
- `internal/mcp/server_info.go` — currently exposes one `mcp_protocol_version` value.
- `internal/mcp/server_test.go` — contains SDK conformance coverage and a raw stdio harness built around the legacy initialization handshake.
- `scripts/interop-smoke.sh` — currently sends only a raw `2025-11-25` handshake before listing and calling MCP features.
- `.github/workflows/foundation.yml` and `.github/workflows/container.yml` — run Codex/Claude native and Docker smoke profiles and must cover both lifecycle eras after migration.
- `internal/domain/pagination/cursor.go` and `internal/domain/pagination/cursor_test.go` — cursors already carry signed continuation state and are stable across codec/process recreation when token, schema, operation version, filters, and page size agree.
- `internal/resources/catalog.go` and `docs/resources-prompts-skills.md` — expose deployment-local pulled schemas and constants; resource reads must not be shared through public caches.
- `docs/tool-contracts.md`, `docs/architecture-spec.md`, `docs/cli.md`, and `docs/interoperability.md` — normative and user-facing documents that explicitly describe the old lifecycle, version, or smoke behavior.

A temporary v1.7.0 upgrade rehearsal compiled all packages. The only test failure was the expected protocol assertion (`2026-07-28` negotiated versus `2025-11-25` expected). After changing the canonical target and regenerating, only the raw legacy test failed because a client requesting `2025-11-25` correctly negotiated that legacy version rather than the new preferred version.

## Implementation Constraints

- Use a stable official MCP Go SDK release; pin v1.7.0 rather than a v1.8 prerelease.
- Keep stdio as the only transport. Adding Streamable HTTP, OAuth, HTTP routing headers, or hosted multi-tenancy is separate work.
- Preserve JSON-RPC-only stdout, centralized secret redaction, fixed production STRATZ endpoint behavior, and current tool execution-error mappings.
- Keep MCP handlers as transport adapters and do not introduce request/session state into domain services.
- Preserve legacy `2025-11-25` negotiation during the compatibility window; modern and legacy lifecycle behavior must have separate assertions.
- Treat `docs/tool-contracts.json` as canonical. Run `make generate` after editing it and never edit `internal/contracts/generated/*`, `internal/contracts/zz_generated.contracts.go`, or `docs/generated-tool-contracts.md` directly.
- Keep cursor encoding and bindings unchanged. Protocol migration must not invalidate existing pagination cursors.
- Keep the current tool names, descriptions, input schemas, and domain semantics. The query-oriented tool-surface refactor is independent.
- Continue publishing Draft 2020-12 tool schemas. The project already uses the schema dialect enabled by the new protocol; broad schema rewrites are unnecessary.

## Assumptions

- Keep the existing `mcp_protocol_version` output field and define it explicitly as the preferred version to preserve consumers of that field. Add `supported_mcp_protocol_versions` rather than renaming the existing field.
- Bump the draft contract version because the required `stratz_server_info` output shape gains a field.
- The canonical supported-version order will match Go SDK v1.7.0 discovery output: preferred first, followed by `2025-11-25`, `2025-06-18`, `2025-03-26`, and `2024-11-05`. Pinning and conformance tests will detect SDK drift.
- Install an explicit v1.7.0 receiving middleware with these initial cache hints: `server/discover` is public for 1 hour; tools/prompts/resources/resource-template lists are public for 5 minutes; resource reads are private with zero TTL because they contain deployment-local restricted artifacts. These are MCP client hints, not SQLite application-cache policy.
- The SDK's `ClientSession.InitializeResult()` remains usable as a compatibility abstraction for checking the selected version, but raw-wire tests will prove that modern requests do not use the legacy handshake.

## Non-goals

- Refactoring or consolidating MCP tools.
- Adding Streamable HTTP or any other transport.
- Implementing MCP Apps, Tasks, multi-round-trip elicitation, or application-level state handles.
- Adding roots, sampling, logging, subscriptions, or server-initiated requests; deprecated capabilities remain unadvertised.
- Changing STRATZ authentication, upstream execution, cache storage, cursor format, GraphQL operations, or normalized domain output.
- Adopting an unstable SDK solely for configurable positive cache TTLs.

## Risks and Mitigations

- Risk: The SDK advertises protocol versions not represented by `stratz_server_info`.
  Mitigation: Pin v1.7.0, keep the ordered list canonical, and compare raw `server/discover` output with generated server-info metadata in conformance tests.
- Risk: A test treats the preferred version as the effective version of a legacy connection.
  Mitigation: Separate preferred, supported, and negotiated-version assertions; retain an explicit legacy raw harness.
- Risk: SDK defaults change list/resource caching behavior on a future upgrade.
  Mitigation: Assert exact zero-TTL/public values and require a conscious policy update with any SDK bump.
- Risk: Public cache scope exposes deployment-local resource contents.
  Mitigation: Mark resource reads private with zero TTL; apply public positive TTLs only to static discovery and catalog-list metadata, never STRATZ tool-call results.
- Risk: Modern raw calls accidentally rely on prior discovery or connection state.
  Mitigation: test a valid modern tool/list request as the first request on a fresh server process with all required metadata carried in that request.
- Risk: Updating the protocol target silently invalidates existing signed cursors.
  Mitigation: leave cursor format, signing inputs, schema version, and operation versions untouched and keep restart-stability tests in the migration gate.
- Risk: Protocol migration expands into unrelated HTTP, extensions, or tool redesign work.
  Mitigation: enforce the non-goals and land those capabilities through separate plans.
